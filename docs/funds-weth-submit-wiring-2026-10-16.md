# Gated WETH submission wiring

The WETH component and production API now have a distinct `weth-conversion` release-policy path. `liveExecutionEnabled` still always returns false, with no environment or request override. The API refuses submission before limiter/storage/RPC when this path is blocked. Only the separately gated submission branch may call eth_sendRawTransaction, using the same durable wallet ledger and scope as other EVM transactions. Preparation, preflight and reconciliation retain read-only RPC.

The component shows a separate explicit consent checkbox and exact-conversion submission button, disabled by the current policy. Consent is cleared when inputs change, files are imported/restored, submission starts or reconciliation starts; it is never persisted. Attempted/recovery-only transaction identities are retained in an in-memory hash Set so reimporting the same signature cannot re-enable submission. Loading a saved recovery copy or reconciling enters recovery-only mode conservatively, including UNKNOWN. Distinct fresh requests remain separate. The server journal remains the authority against duplicates across processes or browsers.

The real component and production POST handler reached a real disposable PostgreSQL journal, survived an actual database restart and browser reload, and reconciled UNKNOWN without resending. These are production-handler HTTP adapter tests with actual Chromium and actual local PostgreSQL, not a full Next server/runtime or hosted Neon campaign. The rate limiter uses the disposable test owner; wallet claims use its restricted role. RPC chain state and lost acknowledgement are synthetic; signatures come from the source key core. No guest signing, external RPC, public transaction, funds readiness or finalized settlement is claimed. No offline protocol/key-core files changed. The local harnesses clear inherited secret/config environment, restrict browser origins and server network transports, and do not persist raw guest files or signing material in reports. Future acceptance still requires the exact released image, complete Next/deployment boundary, current authenticated contract identities, independently reviewed release scope and actual pilot acceptance before any funded policy change.
