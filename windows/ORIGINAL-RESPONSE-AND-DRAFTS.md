# Original response recovery and local draft lifecycle

A wallet-valid signature cannot by itself prove that imported bytes are the original response to an uncertain attempt. New signing attempts therefore retain an immutable, encrypted response commitment before any successful response export. The commitment hashes the complete response in a separate versioned domain, using canonical JSON. It binds transaction bytes/hash, approval signatures, identity and timestamp, while permitting harmless JSON key reordering.

Recovery requires the original attempt, matching request, selected wallet, commitment and independent cryptographic verification. The native review defaults to Cancel. It imports only the same committed response into encrypted recovery; it creates no signature, resets no claim, reprices no transaction and broadcasts nothing. The renderer receives metadata only. Existing healthy historical attempt records can acquire commitments from their already retained original bytes without signing again. An older unknown attempt with neither original bytes nor a commitment remains blocked; a new file cannot manufacture that missing evidence.

The signing-commitments-v1 journal participates in protected-key preservation. Missing, replaced or damaged keys and malformed/conflicting records preserve ciphertext and fail closed. A commitment-only record can identify a recoverable response when both raw-response journals are unavailable. The original attempt stays immutable before and after recovery. If storage fails during import, the external file is untouched and no new authority is created.

New locally prepared chain drafts retain explicit handoff provenance. File exports persist exposure immediately before writing the actual request, after the native save picker has accepted a destination. Canceling that picker creates no exposure. Exchange-folder writes use the same durable barrier. Once a write is attempted, exposure remains recorded across failures/restart, even if the app cannot establish which bytes escaped. Successful exports retain their completion evidence. Imported requests are marked external; earlier records are never relabeled as safely local.

Discard is terminal and preserves the original request/history. It is available only for known local chain drafts with no handoff, response, signing attempt, commitment or prior private spend authorization. Existing wallet guards are checked again before the terminal write. This permits a separately prepared fresh request and fresh review, without changing or deleting the discarded one. Discard does not revoke an exported request, signature, provider authorization, funded bridge or onchain route. Private proof-backed requests, deposits whose prior proof authority is not fully represented, and imported/exported/legacy-unknown requests cannot be treated as safely unsigned.

An application deadline never proves a signature absent or revoked. The native/offline physical device, real positive approval/file handoffs and installed-mainnet qualification remain separate release gates. These controls do not turn synthetic proofs, fixture dialogs, local validators or historical receipts into live qualification. Production private capabilities remain closed until qualified.
