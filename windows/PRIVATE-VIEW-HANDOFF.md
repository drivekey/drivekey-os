# Encrypted private viewing and proof preparation

The online app creates a v30 request for an exact Ethereum v13 or Solana v15 preparation draft. It retains a fresh X25519 transport private key in a DPAPI-encrypted `view-sessions-v1` journal before the public request can be exported. The request binds the complete wallet identity, chain, canonical asset, amount, recipient, encrypted input notes, nonce/fee/rent limits, deadline and transport public key. Speculative pending leaves and unrelated fields are rejected.

The offline Companion imports the public request, verifies its wallet and lifetime, and requires verified separate backup, passphrase and default-Cancel native review. The review explains that a nullifying key grants sensitive access to the Hinkal identity, including other balances and incoming transfers. Application scope and expiry do not cryptographically revoke a disclosed view key. The user must compare the original fingerprint and transport key with the requesting computer. No circuit authorization, transaction signature or submission is implied by this approval.

A one-use offline worker signs only the pinned Hinkal login message to reconstruct the existing deterministic identity. It exports neither that signature nor the spending private key. It seals the nullifying key and public spending point using ephemeral X25519, HKDF-SHA256 with the original request fingerprint and AES-256-GCM. Associated data binds the request and both transport public keys. A separate wallet-domain signature authenticates the exact sealed response. Canonical DER/base64 encodings, key types, ciphertext bounds, full wallet, signed context and deadline are validated. Completed responses retain their validated signing-start time and historical verification after delivery crosses expiry. A new authorization still enforces current expiry.

`SigningAttempts` now recognizes the `private-view` authority. Its irreversible encrypted claim precedes the key-bearing child; original sealed response bytes and commitments survive canceled exports, invalidation and restart. Unknown outcomes block new wallet signing and can only recover the committed original response. The original-response recovery controller verifies the complete v30 wallet and bytes. No reset or automatic re-signing endpoint exists.

On the online computer, the sealed response must match a locally retained original request/session. A separate network worker receives only the transport decryption key, sealed view, original request and public wallet. It has no vault/password/login signature/spending private key and has no sign/finalize/submit dispatch. It verifies the wallet signature, opens the view only with the matching original key, checks current scope, and passes read-only capability to the pinned SDK preparation helpers. The returned public job is checked for exact original context, size and secret leakage, then wrapped in the existing v28 product proof request. The original spending point cannot be changed by provider mutation. The offline Companion must independently reconstruct and authorize that proof; the chain transaction still needs a separate review and signature.

The controller claims a provider attempt before networking. A timeout, outage or interrupted result publication never automatically repeats that request. A completed public job is encrypted before later UI/window checks, and duplicate preparation returns the retained original. Request, response and unsigned proof-request exports use real native file dialogs. Canceled destinations preserve originals. There is no plaintext viewing-key export, renderer key field or key-returning preload method.

Five added protected journal purposes are `view-sessions`, `view-requests`, `view-responses`, `view-job-attempts` and `view-preparations`. Their records and temporary/case-varied fragments participate in the existing fail-closed key-preservation scan. Missing, mismatched or damaged keys cannot create replacements over old records. Wallet removal and uninstall acceptance still require independent preservation/recovery evidence.

The gated functional Review panel supports request creation, offline viewing approval, sealed-response import, public proof-job preparation and original re-export/history. It currently uses exact base units, explicit nonce/fee/rent bounds and encrypted-note input. Native balance discovery/note selection, automatic independently verified preflight estimates, the separate Solana deposit workflow, local swap preparation profiles, provider finalizers and complete settlement remain unfinished. The production capability and all mutating view channels/workers remain closed pending qualification. This integration must not be described as a released complete private wallet.

Local tests use genuine unfunded EVM/Solana signatures and encryption, real Windows DPAPI, and explicit native-dialog/provider/renderer doubles. A fresh unfunded actual Ethereum provider preparation also succeeded in a separate network process without API credentials, circuit authorization or blockchain signing. It is not native/physical/mainnet transaction qualification. The original encrypted synthetic session and unsigned provider job are retained outside the source/deliverables. Final hashes still require independent review.
